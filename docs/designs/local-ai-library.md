## Problem Statement

Explore what an on-device model can do on a phone with no network: capture photos and voice, keep them in a private library, and talk to the assistant about that library. The solution is general. The use cases are test scenarios that prove it:

- U1 Medical records. An older, non-technical user photographs medical records. The app explains what they say in plain language, defines the jargon, lists next steps the records state, and builds a health history as more records arrive.
- U2 Home inspector. Works in a basement with no internet. Asks how equipment works, adds photos to a library, and attaches voice notes to the last photo added.
- U3 Cert prep. Tabled until how people would use it is explored further.

## What Makes This Cool

Everything runs on the phone in airplane mode: voice in, photo understanding, answers spoken back, and a library that stays on the device. For the local AI meetup, the demo is a basement walk-through with the network off.

The second idea is "the model reads, code computes." OCR reads text, the model labels and phrases, and deterministic code does every lookup, comparison, date and number. Example: OCR reads a water heater data plate, the model labels which line is the serial, code decodes the serial into a manufacture date, and the assistant says "built March 2009, 17 years old."

## Target and Existing Code

This plan targets the gemma-voice app (`chrishonson/gemma-voice`). It extends that app and does not start a new one. The speech loop already runs in the app, and no card rebuilds it:

- `voice/`: Silero VAD (`SileroVad`), Parakeet TDT 110M STT (`ParakeetSpeechToText`), `Endpointer`, transcript-based wake word matching (`WakeWord.kt`), clause-level TTS (`ClauseChunker`, `AndroidSpeechSynthesizer`), tuned in `VoiceConfig`.
- `chat/ChatStore`: the MVI store that runs the loop, including the 6 s follow-up window, overheard context and barge-in.
- `llm/`: `LlmEngine` and `LiteRtLlmEngine` running Gemma 4 E2B. `model/ModelRepository` handles the download.

The wake word is not fixed. It comes from `VoiceConfig.wakeWords`, a list where an empty list means always listening. The C4 grammar and every feature match whatever that list holds and never hardcode a name. This doc writes it as <wake word>.

New work plugs into this loop. The C4 grammar runs on the transcript inside `ChatStore` before the LLM call, and new features add intents and state to the existing MVI contract. Persistence, retrieval, validation and export live in their own services (C12), not in `ChatStore`.

Facts about the current code that the plan changes, so no card assumes them:
- `LiteRtLlmEngine` keeps one `Conversation` across requests, and `ChatStore` adds overheard speech to the prompt. C13 changes this for library questions.
- `ChatStore` streams clauses to TTS while the model generates. T3 and T6 change this for checked answers.
- `AndroidSpeechSynthesizer` prefers an installed offline voice but falls back to the engine default, which can use the network. N7 changes this.
- `LlmPrompt` supports text and audio only. Image input needs a new prompt type and engine support (F2.4).
- The manifest sets `allowBackup="true"`. C10 changes it.
- `ModelRepository` downloads with `HttpURLConnection`, resumes partial files, and `ChatStore` enforces the Wi-Fi rule (C9).

## Constraints

- Gemma 4 E2B (`gemma-4-E2B-it.litertlm`, 2.6 GB) on LiteRT-LM. The engine runs `Backend.CPU()` today. GPU throughput and image input are unmeasured on the Pixel 9 Pro.
- Strict MVI (`docs/ARCHITECTURE.md`). KMP, Android first. Every step is tested on Nick's Pixel.
- Library content stays out of logcat unless the user opts in. This covers prompts, replies, OCR output, transcripts and health history entries. Prompt and reply text are already excluded.

## Premises

- P1. One general app. U1 and U2 are test scenarios, not separate products.
- P2. Respect the local model's limits. It never computes values, diagnoses, doses or grades free text. Code retrieves the source items and attaches their IDs, and the model only phrases an answer from what it was given. (Revised after the second opinion: a small model attaches plausible but wrong citations.)
- P3. Heavy reasoning can be pre-digested off-device into downloadable packs. On-device web search is also to be explored.
- P4. Offline by default. Any network use is per request, opt-in, and visible.
- P5. U2 is the first slice. A disclaimer button sits at the top of every screen where it cannot be missed. It explains the limitations and the accuracy measures taken, and it states that accuracy is never guaranteed.

## Approaches Considered

- A, Minimal. One generic library of photos, voice notes and text, with the voice assistant over it. U2 first. Effort M, risk low.
- B, Ideal. Typed collections with config-driven views and grammar, downloadable packs, on-device retrieval with embeddings, and modes per use case. Effort XL, risk medium.
- C, Lateral. A build-time pipeline digests content into packs with a cloud model, and the device only retrieves, speaks and drills. This mostly served U3, so it is deferred with U3 except as the pack source for N5.

## Recommended Approach

A first, growing into B. Slice 1 templates are data only: prompts, safety text, safety trigger rules and field labels. Views and the voice grammar stay in code. Packs (C) come in later as reference content.

## Functionality

### Shared core

- C1 Library. Item kinds: photo, voice note (audio plus transcript), text note, and document (an ordered set of page photos). Each item has a stable ID, a created time, its collection, OCR text, and model output stored separately and flagged as generated. Stored in app-private storage with a local SQLite database.
- C2 Collections. Named groups such as "123 Main St" or "Mom's records". Each has a template (generic, inspection, health). In slice 1 a template is JSON data: prompts, safety text, safety trigger rules and field labels.
- C3 Capture. In-app camera with a large shutter. Each capture becomes the collection's "last item", the attach target for voice notes. The target is resolved to a fixed item ID when the command starts (the utterance begins), not when transcription finishes, so a capture or collection switch during transcription cannot redirect the note.
- C4 Voice commands. Runs in the existing loop in `ChatStore`. A fixed grammar in code handles commands first: "note ...", "what is this", "read that back", "new collection ...", "undo". Only free questions go to the model. A 2B model does not call tools reliably, and a grammar can be tested. Each command gets an ID. A voice note's audio and transcript are persisted together in one transaction, and a replayed or interrupted command with the same ID cannot add a duplicate. "Undo" reverses the most recent command by its ID in the current collection, one step only, and the assistant confirms ("Removed note on photo 7").
- Voice commands grammar & rules:
  - **Grammar**: Case-insensitive pure function. Strips leading greetings (`hey`, `hi`, `hello`, `ok`, `okay`, `yo`, `uh`, `um`), any configured wake word from `wakeWords`, and punctuation, then matches anchored at start: `note on photo N <text>` (N is digits or one..twenty), `note <text>`, `read that back` / `read it back`, `new collection <title>` (optionally with ` at <address>`), `undo` / `undo that`.
  - **General knowledge**: Marked when transcript, after stripping, starts with `what is this`, or starts with `how does` and contains `work`, `in general` or `generally`.
  - **Target & ID rules**: Target is resolved at utterance start (`fixTarget()`), not when transcription finishes. Voice notes are written atomically with a unique `commandId`; replays are idempotent. Undo tracks per-collection history and reverses only the most recent command of the current collection.
- C5 Ask. A library question draws on the current item, then the collection, and stops there (T7). General knowledge is used only when the request asks for it, which the C4 grammar decides from fixed phrases: "what is this", "how does ... work", "in general" and "generally". Free conversation outside the library answers from general knowledge as today. Code attaches the source chips (T2).
- C6 Text extraction. On-device OCR (ML Kit Text Recognition, bundled model) supplies all verbatim text, including identifiers on equipment such as serial and model numbers. The model may label which OCR line is which field, but quoted text, numbers, dates and identifiers always come from OCR, never from the generator. Gemma vision supplies scene descriptions only.
- C7 Retrieval. Slice 1 uses SQLite FTS keyword search over OCR text, transcripts, user notes and generated photo descriptions. Embeddings come later, if FTS misses too much.
- C8 Export. Export a collection as PDF or markdown (an inspection report, or a health summary for a doctor visit) through the Android share sheet, started by the user.
- C9 Model management. Extends the existing `ModelRepository` download, which already resumes partial files. New work: Wi-Fi only by default, with the size shown first.
- C10 Storage privacy. New work: Android Auto Backup is disabled (today `allowBackup="true"`. It becomes `false`, and data extraction rules exclude the library), so nothing reaches Google Drive. Health collections are encrypted at rest with a key held in the Android Keystore, covering images, audio, the database, its FTS index and temporary files. Explicit backup stays open as Q8.
- C11 Network gate. Every network request the app makes goes through one app-level client that logs each request. The same client drives the N2 indicator. It cannot see traffic from platform services such as TTS, so N7 and S1 cover those separately.
- C12 Services. `LibraryRepository` (storage), `Retriever` (C7), `Validator` (T3, T6, T7, T8) and `Exporter` (C8) are separate classes behind interfaces. `ChatStore` and new MVI stores call them from intents and keep immutable state. `ChatStore` does not grow persistence, retrieval or validation logic.
- C13 Context isolation. Each library question starts a fresh LiteRT-LM conversation (`resetConversation`) holding only the system prompt, the retrieved items and the question. Overheard speech is not added to library questions. A question is scoped to one collection, and a health question to one person. Free conversation outside the library keeps today's behavior.

### Trust and accuracy

- T1 Disclaimer button. Pinned in the top bar on every screen, in a distinct color, labeled "Limits". It opens a sheet covering: what the model is (small, offline), how it fails (misreads, invented facts, wrong attribution), the measures present in this build, and "Never guaranteed. Verify with a professional." The sheet lists only the T items the build actually ships, read from the same feature config, so it never describes a safeguard that is absent. The first launch opens it and requires an acknowledgement. Each template adds its own text, such as health or electrical safety.
- T2 Code-attached sources. Chips show the items the model was given, labeled "Consulted", not "Supported". A chip says an item was read, not that it backs every claim. When no retrieved item was used, code adds a fixed "General knowledge, unverified" label, and an answer that used retrieved items carries that label too when T3 or T6 flags content. A chip that points at generated text says so ("Generated description of photo 12").
- T3 Value check. After generation and before any speech or export, code normalizes and checks every number, date and dose in the output against the cited source text, which for a T8 field is the confirmed value. Normalization covers numerals and spelled-out numbers, units, and common date formats parsed to one form. Any value not found is highlighted and marked unverified. In general-knowledge answers, every number is marked unverified, because there is no source to check. Known blind spot: a correct value attached to the wrong label passes. For lab results the label binding comes from table reconstruction (F1.4), not from the model. The model never states computed values (T8), so T3 has nothing extra to match for them. T3 is deterministic and unit-testable. Streaming rule: an answer streams only when its prompt holds no library content (no OCR text, notes, transcripts or quotes), which means free conversation and the general-knowledge requests in C5. Those answers start with the spoken "General knowledge" label, and every number is marked unverified clause by clause as it arrives, which needs no full-answer check. Any answer whose prompt holds library content does not stream. Generation finishes, T3 and T6 run, and only then is the answer spoken, shown or exported. Text that fails a check is spoken and shown as unverified, never silently passed, except under the T8 computed-value rule, which drops the sentence.
- T4 Fixed safety responses. Each template defines trigger rules (keywords and phrases) that code runs on the transcript before generation. The trigger gate is built in the shared check step (X8) and runs before every generation, so no card generates an answer without it. Templates supply only the rule content. The must-catch electrical list ships with the gate in X8. Emergency, dosing and diagnosis triggers replace the model's answer with prewritten text ("Call your doctor" or "Call 911"). Electrical triggers that ask how to do live or panel work ("how do I replace", "wire", "fix the breaker") replace the answer with prewritten text and no model output: "Treat the panel as live. The service conductors stay energized even with the main off. Use a licensed electrician." Questions about how equipment works get the same safety line first, then the model's explanation, which the template prompt limits to how it works, not procedures. Keyword rules will miss some phrasings and misfire on others, such as negations. The T1 sheet says so, and S7 measures both.
- T5 Generated marking. Model output is shown in a distinct style and never mixed with extracted text.
- T6 Quote check. Before any speech or export, any span the model presents as a quote must be a normalized exact substring of the cited page's OCR text, or of the confirmed value for a T8 field. If it is not, the quote marks are removed and the text is marked unverified. T6 proves the quote matches OCR or the confirmed value, not that OCR read the page correctly. T8 covers that.
- T7 Cannot determine. When retrieval finds nothing above a relevance threshold for a library question, the assistant says it cannot find that in the collection ("I don't see that in Mom's records") instead of answering from general knowledge. It answers from general knowledge only for the explicit requests in C5, with the T2 label.
- T8 Confirmed fields and provenance. OCR values that feed a computation or enter the health history (patient name, record date, medication, dose, lab value, serial number) are shown as the cropped page region beside the OCR text, and the user confirms or corrects each one before use. Corrections are stored as user edits, and the original OCR is kept. A confirmed or corrected value is the evidence T3 and T6 check against, shown as "confirmed by you" or "corrected by you" beside the original OCR. Fields outside T8 are checked against OCR. Each item keeps page coordinates for every extracted field. A computed value records its inputs, the rule and the rule version, and is shown as "computed from serial ... by decoder v1". The model never states a computed value. Code speaks and shows it from a fixed sentence ("Built March 2009, 17 years old, from the serial number"), and the model may only add explanation after it. Its prompt does not contain the computed value, so it has nothing to restate. In an answer that carries a computed value, code drops any model sentence holding a number that is in neither the source nor the computation inputs, instead of speaking it as unverified. So the explanation after a computed value carries no general-knowledge numbers, such as typical service life. Those wait for a reference pack (N5) that supplies them as a cited source. Nick's decision.

### U2 Home inspector (slice 1)

- F2.1 Inspection collection with a title and address.
- F2.2 Rapid capture. Each photo becomes the last item. The assistant confirms by voice: "Photo 7."
- F2.3 Voice note attach. "<wake word>, note: double-tapped breaker, slot 14" attaches audio and transcript to the last photo, and the assistant replies "Noted on photo 7: double-tapped breaker, slot 14." Saying "note on photo 5" targets a specific photo.
- F2.4 "What is this?" sends the last photo to Gemma vision. The answer is labeled general knowledge. Image input needs a new `LlmPrompt` type and `LiteRtLlmEngine` support whatever X0 finds, because the contract supports only text and audio today. The assistant says "Looking" at once as feedback, which does not make a slow answer acceptable. Fallback, decided by X0: if image prefill plus first spoken clause exceeds the S6 target, or LiteRT-LM has no image input for E2B, the model gets OCR text plus ML Kit image labels as text instead. If the text fallback also misses the target, F2.4 leaves slice 1 and S1.
- F2.5 Explain. "How does a main panel work?" is answered from general knowledge with the electrical safety text (T4). Later the answer is grounded in a pack (N5).
- F2.6 Hands-free mode. Wake word on, screen kept awake, large controls.
- F2.7 Review and export. A photo list with notes and a generated draft caption per photo (T5), exported per C8.
- F2.8 Data plate read (slice 1, one brand). OCR reads the plate, the model labels the brand, model and serial lines, the user confirms the serial (T8), and code decodes the manufacture date for one brand and reports age with its derivation (T8). This tests "the model reads, code computes" directly, so it comes before general explanations.

### U1 Medical records (slice 2)

- F1.1 Health collection per person. Retrieval and model context never cross persons (C13).
- F1.2 Multi-page document capture with edge detection and crop.
- [x] F1.3 Explanation per document, in three parts: "What this says", "Words explained" (a jargon glossary), and "Questions to ask your doctor". Each part carries T2 chips and passes T3 and T6 before it is read aloud.
- F1.4 Lab results. Code reconstructs the table from OCR bounding boxes, binding each value to its test name, unit, range and the lab's own printed high or low flag. When a row cannot be reconstructed, the app shows the cropped page image beside the raw OCR lines. The model never judges values.
- [x] F1.5 Health history. A timeline of conditions, medications, procedures and results built from the records. The user confirms each entry before it enters the history, and every entry links back to its source page.
- [x] F1.6 Next steps. This covers only follow-ups the records state, quoted with their source and checked by T6 ("repeat in 3 months"), plus questions to ask. It is not advice beyond the record. This narrows "advice about next steps" in the brief to fit P2.

- F1.8 Share. A health summary PDF for family or a doctor, per C8.

## Model Capabilities

Can do. T2 to T8 catch some of the errors, within the limits stated in T3 and T4:
- M1 Voice conversation.
- M2 Rewrite given text in plain language.
- M3 Summarize a short document that fits in context.
- M4 Describe what a photo shows.
- M5 Explain from general knowledge. This is the least reliable item and is always labeled.
- M6 Label which OCR lines hold which fields.

Cannot do, or must not be trusted with:
- M7 Read dense tables or identifiers verbatim through vision. OCR and table reconstruction do this.
- M8 Arithmetic, unit conversion or date math. Code does this.
- M9 Diagnosis, dosing or triage.
- M10 Authoritative electrical code compliance answers.
- M11 Reliable tool calls, multi-step agent loops, or safety classification.
- M12 Reason over a whole collection at once. Retrieval narrows the input first.
- M13 Grade free-text answers. This is noted for U3.
- M14 Cite its own sources. Code attaches them (P2).

## Offline and Online

- N1 Every C, T and F item works in airplane mode once the model is downloaded. This is an acceptance test.
- N2 An indicator in the top bar shows whenever the C11 client has a request in flight.
- N3 The model download is the only network use in slice 1.
- N4 Web search (explore). A fixed pipeline runs search, fetch, extract on device, then summarize with links. The user starts it per answer. The query leaves the device, so the app says so first. Health collections cannot use web search at all until N4 is designed.
- N5 Packs (later). Downloadable reference content, pre-digested off-device, such as equipment service life, serial decoders or a medical glossary. They carry versions and sources.
- N6 No cloud LLM fallback in v1. This keeps the local claim honest.
- N7 Offline speech only. TTS must use an installed offline voice. If none is installed, the app says so on screen and answers in text only, instead of falling back to the engine default voice, which can use the network.

## Success Criteria

- S1 U2 on the Pixel: 10 photos captured, voice notes attached hands-free, "what is this" answered, report exported. Run once in airplane mode and once with the network on. In the network-on run, the C11 log shows zero requests and an independent check (Android per-app data usage, or a capture on the access point) shows no traffic from the app or from TTS.
- S2 Voice notes attach to the intended photo in 100% of a scripted test, including races: a new capture during transcription, a collection switch mid-note, and an interrupted or replayed command. No duplicates.
- S3 Retrieval and answer support on 30 scripted questions over a library from a staged walk-through Nick records (about 200 items). Nick scores in two stages. After X7, whether the code-chosen chip is relevant. After X8, whether the item supports the generated answer. Target: at least 90% on both. Five more questions the library cannot answer must get the T7 "cannot find" response.
- S4 U1: a synthetic lab report explanation passes T3 and T6, and the glossary covers a fixed expected-term list written for that report.
  The fixture test is PlainLanguageExplainerTest.
- S5 The disclaimer is visible on every screen, the first launch requires acknowledgement, and the sheet lists only shipped T items.
- S6 Latency targets are set after Q2.
- S7 T4 trigger tests per template, with pass bars. A fixed must-catch list (emergency, dosing, diagnosis, live electrical work) hits 100%. A paraphrase list hits at least 90%. A list of non-triggering and negated phrasings misfires at most 5%. A miss on the must-catch list blocks release. The thresholds are Nick's to revise.
